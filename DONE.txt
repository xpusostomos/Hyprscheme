== THE LOADER (init.scm owns the module list) ==
- init.scm is the ONLY list of modules, and the ONLY thing the host
  loads. Host.cpp names no module at all: it creates the kernel and
  registers the gsubrs, makes the generation, makes it CURRENT, then
  one evalFile(init.scm) — so init.scm's `use-modules` ARE the
  generation's environment, stdlib included. The 23-line useModule()
  list that duplicated init.scm's and could drift from it is GONE.
- init.scm's `in?` was a load masquerading as a probe. `resolve-module`'s
  second POSITIONAL arg is `autoload` (default #t) and `#:ensure` is a
  separate switch, so `(resolve-module name #:ensure #f)` still LOADED
  the file and answered "already in" for a module never loaded. Every
  module's body therefore ran TWICE on generation 1, and the macro's
  `use-modules` branch was dead code that never once executed.
- The probe is now `(resolve-module name #f #:ensure #f)` AND a
  `module-filename` check. Autoload off is not enough on its own: a
  module can exist with no file behind it. `(hyprscheme)` is the parent
  of every `(hyprscheme X)`, so the tree grows it as a directory module
  as soon as the first family is defined, and `reload-module` on it
  fails ("unknown file name for module"). Verified the hard way —
  without the check, the last line of init.scm dies on gen 1.
- The macro reloads if present and then ALWAYS imports: `reload-module`
  does not import, so gen 2+ would otherwise get nothing. Guile's own
  modules (the five stdlib ones) use plain `use-modules` — `reload-module`
  on one is an error, not a refresh.
- The umbrella is LOADED but not IMPORTED, deliberately: importing it
  would make a config's environment depend on the re-export list, so a
  public name added to a family but not yet to the umbrella would go
  missing from configs.
- tests/t-generation.sh pins it, asserting the generation's own USE-LIST
  rather than that a call works. Guile resolves names through a used
  module's use-list transitively, so with the old order the generation
  still REACHES everything and the whole rest of the suite passes — only
  the use-list shows it. Verified to fail by restoring the old order
  (names all 18 missing modules).
- tools/load-check.scm mirrors the new order: the generation is made
  before init.scm and is the module init.scm is read in.
- FIVE dead hl:: helpers removed from Guile.hpp/Guile.cpp, with the
  private thunks and includes that only they used (callThunk0,
  moduleCall1Thunk, ModuleCall, <sstream>, <vector>):
    useModule   — orphaned by this work: the import list moved into
                  init.scm and no caller was left
    exportAll   — the kernel exports by #:export now, not module-export-all!
    resolveModule — a byte-for-byte duplicate of makeModule, which superseded it
    loadModule  — init.scm loads modules by name
    call0       — nothing makes a 0-arg contained call
  The last four were already dead before this work. Kept: the
  define-module-expands-in-the-CURRENT-module insight, which is live
  (load-check.scm implements it) and now lives in CLAUDE.md with
  loadModule marked dead rather than as a claim about live code.
- tools/bind-audit.py now REPORTS dead helper declarations in Guile.hpp,
  so this class cannot silently re-accumulate. Verified to fail: adding
  `SCM nothingCallsThis(const char*)` trips it, exit 1, naming the
  offender. The check is exact (hl::-qualified mentions only) precisely
  because a bare-name search matches same-named members across the tree
  and would be disabled as noisy.
- makeModule's comment corrected: it claimed `#:ensure` is what makes it
  create on a miss. It is the C entry point scm_c_resolve_module, which
  has no such argument — it creates on a miss AND autoloads.

  as the Host.cpp list: a hand-kept list of what is public drifts from
  what is public, and this one had — it listed hl-bind-thunk and

- Consumers rewired: doc-audit.py (glob the modules), doc-exercise.scm

- Docs: CLAUDE.md's umbrella section rewritten as "THERE IS NO UMBRELLA"

== ENUMS: a name for a set of values ==
- NEW MODULE (hyprscheme enums) — a LEAF like core (imports the kernel
  only, no compositor knowledge), so every family may import it.
  module-audit's rule is now stated around a SHARED set (kernel, core,
  enums) rather than "kernel and core".
- The machinery: <enum-values> (make-record-type) carrying BOTH an ass
  list symbol->integer and an rnrs enum over the same symbols.
  make-enum-values, define-enum-values (sugar), enum-values?,
  enum-value (takes EITHER spelling, returns the integer — so an API
  function accepts a symbol or an integer with no conversion code of its
  own, and a value outside the set is an ERROR naming the set),
  enum-symbol (the inverse; what a getter returns),
  enum-values->enum (the rnrs enum, for the whole (rnrs enums) toolkit).
- The two numberings are INDEPENDENT and both kept: rnrs numbers members
  0..n-1 in declaration order, the API integers are the compositor's
  (fullscreen-mode is -1/0/1/2). Pinned by a test ('keep has rnrs index
  0 but value -1).
- The error names the set in the CALLER'S OWN CURRENCY: a bad symbol is
  answered with the symbols, a bad integer with the integers.
- (rnrs enums) is now imported into the generation (init.scm) — without
  it enum-values->enum returned an inert object and "you also have the
  rnrs toolkit" was false.
- RULE written into CLAUDE.md ("API conventions -> ENUMS"): a function
  taking or returning one value from a fixed set speaks in symbols and
  the set is a named enum. No bare integers, no strings.
- Enums shipped: fullscreen-mode (keep none maximized fullscreen),
  fullscreen-handler (none default layout scrolling).
- tests/t-enums.sh. Everything wired into the tools that have their own
  module lists: compile-lint, load-check, doc-exercise.

== FULLSCREEN: modes as symbols, Lua's three actions ==
- hl-window-fullscreen and the NEW hl-window-fullscreen-client return a
  MODE SYMBOL ('none/'maximized/'fullscreen), and
  hl-window-fullscreen-handler returns a handler symbol. All three take
  #f for the focused window (the mode getter used windowOf, so it raised
  on #f while its maximized? partner accepted it).
- hl-window-fullscreen-set! is now the Lua shape: #:mode
  ('fullscreen default | 'maximized), #:action ('toggle default | 'set |
  'unset), #:layout-aware (#t default, the dispatcher's own). 'set and
  'unset are IDEMPOTENT — no-ops when already as asked — which is what
  stops "unset fullscreen" on a maximized window from clearing maximized.
  (The old #:on? #f wrote FSMODE_NONE, wiping whichever mode was set.)
- hl-window-fullscreen-sync! takes mode SYMBOLS too, 'keep meaning
  "leave this side alone" — still the only way to set the client side, and
  now the documented way to fullscreen a window WITHOUT telling the app.
- hl-window-maximized-set! REMOVED (redundant under #:mode; Lua has no
  second dispatcher). hl-window-maximized? stays.
- C++: new gsubr hl--c-window-fullscreen-client; the toggle gsubr gained a
  layoutAware argument (it hardcoded false, so OUR toggle could not be
  layout-aware while Lua's can); hl--c-window-fullscreen-set REMOVED — the
  rewritten setter uses only the toggle, exactly as Lua's does, and
  bind-audit flagged it dead.
- CORRECTION to an earlier claim of mine: the client side IS told by
  default. `syncFullscreen` (a per-window property, DEFINE_PROP default
  TRUE) makes setFullscreenMode sync client to internal when client is
  absent — so the 3-arg DOES reach the app unless sync_fullscreen is off.
  Caught by a test I wrote asserting the opposite; the docstrings and the
  wiki were wrong and are fixed.

- hl--error -> (error MESSAGE ARGS ...): Guile builds the message by
  appending one ~S per argument, so the value lands at the end. 94 sites

- hl--record-field -> Guile's record-accessor, bound once per field. 16

== THE BOUNDARY: bools, symbols, and one decision that was in the wrong place ==
- Arg<bool> added to Bindings.hpp: a C++ bool parameter takes a Scheme
  BOOLEAN by truthiness (scm_is_true). #t is a distinct immediate, not a
  number, so Arg<int> refused it outright — "argument 3 is not an
  integer" — and that is why 19 gsubrs had `int` params with call sites
  writing (if x 1 0). All 19 converted to `bool` + the conversion
  dropped. TRAP: 0 is TRUTHY, so a site left passing (if x 1 0) would
  invert.
- Arg<const char*> takes a SYMBOL as well as a string. A name-ish
  argument (config key, tag, prop) is what Scheme has as a symbol, and
  requiring symbol->string at the call site was 40 conversions. Numbers
  are deliberately NOT accepted — a number means a name only in the
  workspace/monitor resolvers. hl--str went from 40 call sites to 5
  consumers; hl--dir deleted.
- RULE, in CLAUDE.md ("THE BOUNDARY"): a gsubr mirrors the C/C++ call it
  exposes — same shape, just enough to be a sensible Scheme call. Policy
  lives in Scheme. Two violations were real:
  - hl--c-window-fullscreen-toggle hand-rolled an isFullscreen test the
    compositor's own action already does, and threw away an answer
    Scheme had already read. Now hl--c-window-fullscreen-set mirrors
    setFullscreenMode, which SETS.
  - hlCurveAdd(name, int type, a,b,c,d) invented a type argument
    Hyprland does not have — it has TWO calls, addBezierWithName and
    addSpringWithName, and the curve type is WHICH FUNCTION YOU CALL.
    Split into hl--c-bezier-curve-add / hl--c-spring-curve-add, and the
    Scheme API into hl-bezier-curve-add! / hl-spring-curve-add! (the
    variadic . vals and its zero-padding are gone with it).

== hl-load-config reports a load that FAILED (not just a missing file) ==
- hl--load returned #t WHETHER OR NOT the load worked — the guard printed
  the error and then fell through to #t, so a caller could not tell. That
  is how "the config loads but set-mark is unbound" was possible: the
  file died at its 300th form and hl-load-config handed back a path as
  if it had worked. It now returns #f when the guard fires; `load` itself
  still returns #t (Guile's own does, and a config calling it is not
  expected to check).
- hl-load-config raises a DIFFERENT notification for the two failures,
  which are worth telling apart: "config not found: NAME" for a file that
  is not there, and "config failed to load: PATH" for one that raised.
  A missing file is usually a typo; a file that raised has ALREADY
  DEFINED SOME OF ITSELF, so the config is half-applied — the state that
  is hard to diagnose, and the one the notification exists for.
- Tests in t-api.sh, verified to fail: reverting hl--load to answer #t
  always makes the notification assertion fail. t-zzzz-exit's
  allowed-error list gained the error t-api now provokes on purpose.
- Wiki (scheme-utilities.md) and the docstrings say both cases.

== SENT KEYS WERE RESOLVED AS KEYSYMS, NOT KEYCODES (the C-f bug, found) ==
- THE BUG Chris reported as "the key bindings that are mapped to work in
  the browser don't work": hlSchemeSendShortcut and hlSchemeSendKeyState
  resolved the key with xkb_keysym_from_name and handed the KEYSYM to
  Config::Actions::pass. pass() forwards its key straight to
  sendKeyboardKey as `key - 8` — an XKB/evdev KEYCODE, the units of the
  keybind manager's m_lastCode. The two numberings are unrelated, so
  every sent key was the wrong number: "f" sent 94 (not f), and the
  NAMED keys — Right/Left/Next/Prior, i.e. the payload of every chord
  Chris named (C-f, C-b, C-v, M-v) — resolved to ~0xff00, far outside
  the keycode range, and were DROPPED silently. Nothing raised because
  pass() never validates its keycode: actionResult answered 0 and the
  wrappers answered #t.
- WHY IT SURVIVED THE SUITE, the lesson worth keeping: t-crashdir
  asserted that (hl-window-send-shortcut! ...) ANSWERS #t. It did, while
  sending garbage. An assertion on a RETURN VALUE cannot see a wrong
  PAYLOAD. This bug was three weeks old (git blame: 685c20b, 2026-09-26)
  and every lint was green throughout.
- THE FIX: both gsubrs resolve through Keybinds::resolver()->
  resolveKeycode(), exactly as the scripting API's own dispatchers do
  (LuaBindingsDispatchers dsp_sendShortcut/dsp_sendKeyState). It is a
  conversion, not a policy — the boundary is the one place allowed to
  know both spellings. Two side effects: Hyprland's own tokens
  ("code:28", "mouse:272") now work where they were previously refused,
  and a keysym that is not on the LOADED KEYMAP (Cyrillic_a, Arabic_alef
  under `us`) is refused with an error instead of being sent as
  nonsense.
- Query.cpp:142 looks identical but is CORRECT and was left alone:
  isKeysymDown() genuinely takes an xkb_keysym_t.
- TESTS: new tests/t-keydeliver.sh, VERIFIED TO FAIL on the old code
  (7 failures, naming the bug). What it asserts, and why, is measured
  rather than assumed: it CANNOT assert delivered bytes, because pass()
  stamps the event with state()->m_timeLastMs, which only a REAL key
  event sets — under the harness a correct, explicitly-keycoded send
  still delivers 0 bytes to a focused `cat`, with a keyboard present and
  no error. So it pins the RESOLUTION, the half the bug was in and the
  half a harness can see: keycode tokens accepted (only the resolver
  knows them) and off-keymap keysyms refused (only the resolver checks).
  Deliberately NOT asserted: a junk NAME like "notakey", where
  resolveKeycode NoSymbol-matches the first unmapped keycode — upstream
  behaviour, not this bug, and pinning it would encode a quirk.
- Not asserted anywhere and worth saying plainly: END-TO-END DELIVERY to
  a focused app is only observable in a live session. This fix was NOT
  confirmed by pressing C-f in Firefox — that is Chris's check to make.

== THE RELOAD NO LONGER RE-READS THE MACHINERY: an explicit reset instead ==
- The machinery (kernel, core, enums, values, the 14 families, extras,
  emacs-keymaps) is now loaded ONCE per process. init.scm is still read on every
  generation, but every use-modules in it is a no-op after the first — which is
  what the module objects, and the gsubrs the host registered into the kernel,
  rely on. `reload-module`, the `in?` probe and the `use-or-reload-modules`
  macro are GONE from init.scm.
- The cost of that reuse is that a module's top-level state now OUTLIVES the
  generation, where re-reading it used to reset it by accident. A set! from a
  config on an EXPORTED binding writes into the EXPORTING module's cell, so the
  old behaviour was load-bearing: with reload-module removed and nothing in its
  place, t-api's `(set! hl--watchdog-ms 999999)` + reload test kept 999999, and
  t-watchdog failed downstream of it.
- So a module that keeps state defines an UNEXPORTED `reset`, and the sweep at
  the end of init.scm calls them all, once per generation, after every module is
  imported and before the config is read. Written for the only two modules that
  have state — kernel (watchdog budget/rearm/stack/handler) and emacs-keymaps
  (its three submap tables) — and nothing is registered anywhere, so a module
  cannot be forgotten from a list. The sweep runs on every generation including
  the first, where it is a no-op.
- THE SUBTLETY THAT COST THE FIRST ATTEMPT: the sweep iterates `module-uses`,
  which holds each module's PUBLIC INTERFACE, not the module. use-modules is
  module-use! on resolve-interface, and an interface carries only the EXPORTED
  names — so an unexported `reset` is simply not in one. The first version found
  nothing and silently did nothing (calling it by hand returned cleanly and
  changed no value). Probed and confirmed for (hyprscheme kernel): the use-list
  entry has module-kind `interface`, the resolved name has `directory`, they are
  not eq?, and module-local-variable answers #f for the former and the variable
  for the latter. The fix resolves each entry's NAME back to the module.
- `module-local-variable`, not `module-variable`, is the predicate — the latter
  answers for imported bindings too, so a module merely USING something named
  `reset` would look as though it owned one. tools/module-audit.py carries a
  named UNEXPORTED exception for `reset`, with its reason, because its
  every-define-is-exported rule is exactly right otherwise.
- Also fixed: the host clears `hl--ready` BEFORE reading init.scm. The kernel's
  file being re-read each generation used to re-set it to #f; loaded once, it
  would still be #t from the previous generation and the host's "did the API
  finish loading" check would be vacuous.
- Tests: t-api asserts the kernel variable is back to 5000 after a reload, and
  now also that emacs-keymaps' submap table is EMPTY again — reaching the
  unexported table the way the sweep does (resolve the module, take its own
  binding). Verified to fail: the submap assertion reports "[1] want [0]" with
  `(define (reset) #f)` in emacs-keymaps. 20/20 suite; make check clean, 7/7.
- Consequence to know: a machinery .scm edit NO LONGER takes effect on a config
  reload — the plugin has to be loaded afresh (a session restart). The wiki's
  building-the-plugin page claimed the opposite and was corrected, as was the
  loader section of CLAUDE.md.
- PARKED, and worth knowing why: this pass began as a memory-leak hunt. The
  generation module is permanently rooted by Guile — beautify-user-module! calls
  module-name, and module-name on an UNNAMED module names it AND registers it in
  the root module (boot-9.scm:3198; upstream bug#19235, 2014, still open, same
  class as bug#77374, 2025). Measured with a guardian test: make-module is
  collectable, make-module + beautify-user-module! is not, and pre-naming the
  module before beautifying makes it collectable again — but one retained
  generation costs ~5 kB against a ~885 kB/reload leak, so it is NOT the main
  term, and the bulk (~800 kB/reload, fixed, independent of config size, absent
  with the plugin unloaded) is still unexplained. Agreed not to chase a Guile
  design issue; the leak is documented here rather than fixed.

== NO MORE SHADOWS: `load` and `eval` are gone, `hl-load` is public ==
- The kernel used to redefine Guile's `load` and `eval` for every later file:
  `load` so a config's (load "x.scm") landed in the generation, `eval` to match.
  Both shadows are GONE, and neither name is on the kernel's export list any
  more. Machinery that silently redefines a core binding is a trap.
- `hl-load` replaces the load half — a public function in (hyprscheme core),
  exported and documented like anything else, next to the other plumbing. It is
  the same load said out loud, with the target NAMED (hl--c-generation) rather
  than assumed from the current module. It still answers whether the FILE
  loaded (#f when it raised, having reported to the log), which is what
  hl-load-config builds on, and hl-load-config now calls it by that name.
- EVAL NEEDED NO REPLACEMENT AT ALL, which is the part worth remembering: with
  no environment `(eval x)` evaluates in (current-module), and the host leaves
  the GENERATION current after buildGeneration succeeds — the success path
  never restores the old module. So a bare eval was already landing where the
  shadow was putting it; the shadow bought the appearance of control, not the
  thing. Nothing in the machinery or in the test config used a bare (eval ...).
- Where the no-generation fallback goes: hl-load loads into whatever module is
  current, via PRIMITIVE-LOAD and not `load`. Not a style choice —
  compile-lint rejected `load` outright in (hyprscheme core): "Use of `load' in
  declarative module", because a declarative module promises no bindings are
  added at runtime, which is exactly what load does. Verified to fail before
  the fix; the only visible cost is that a RELATIVE path is not searched for on
  %load-path, and every caller passes a path it built.
- The kernel stays #:declarative? #f, but NOT for the old reason — it is
  nothing to do with shadows now. It stays because the HOST modifies the kernel
  after it is read: it assigns every gsubr into the exported placeholders
  (registerAllBindings) and it sets hl--ready. Both reasons are in CLAUDE.md.
- Side effect worth having: the "imported module (hyprscheme kernel) overrides
  core binding `load'" warning is gone from every harness, and compile-lint
  reports zero warnings. NOT "warning-free" overall, and the difference is worth
  stating exactly: the C++ build still emits 72 -Wvolatile warnings, every one
  originating inside /usr/include/guile/3.0/libguile/scm.h's own macros — the
  unavoidable kind CLAUDE.md allows. Nothing in src/ warns.
- Tests: t-zz-example loads examples/hyprland.scm through hl-load — it needed
  the guarded one anyway, since its whole method is diffing the compositor log
  and a bare load no longer logs. t-api asserts hl-load answers #f for the file
  that raises, reusing the same broken file hl-load-config is tested with, so
  t-zzzz-exit's existing allowance covers the second error line. t-coverage's
  introspected list picked hl-load up on its own. 20/20; make check clean, 7/7,
  no lint warnings (see the side-effect bullet above for why that is not the
  same as "no warnings").
- Docs: the wiki's split-config example (core.md) and scheme-utilities.md now
  use hl-load, and both say plainly that bare `load` still works but RAISES —

- STILL OUTSTANDING from the same directive: watching files a config loads from

== WATCHING WHAT A CONFIG LOADED, with inotify bound from Scheme ==
- THE GAP: the host loads exactly ONE file — the config — and nothing in it says
  what it reached, so a (hl-load "…") pointing outside the config's directory was
  invisible: no watch, no reload, silent. The INTERPRETER knows, because it did
  the loading.
- THE SHAPE, which is the part worth copying later: %load-hook (Guile's own "a
  file is being loaded" notification) records every path the loader reads; the
  machinery watches each one's DIRECTORY and reloads an event that matches a
  recorded path. The only C++ is ONE GENERIC PRIMITIVE — hl--c-on-readable, "call
  this thunk when this fd is readable" — which knows nothing about inotify or
  config files and is reusable for any fd. Every decision stayed in Scheme.
- INOTIFY ITSELF IS BOUND FROM SCHEME with (system foreign) — no C, no
  dependency. (hyprscheme inotify) is the libc boundary module and is EXCLUDED
  WHOLESALE from the API by tools/api-names.scm, alongside the kernel, with the
  reason written down: it is a table of foreign bindings, not API, and its names
  are inotify(7)'s on purpose so they can be checked against the header.
  (hyprscheme watch) is the policy — a composer, since it calls
  hl-config-reload!, which a family owns.
- WHY THIS AND NOT THE ALTERNATIVES: Guile has no inotify of its own (verified:
  no symbol in libguile, no file in its tree) and the third-party guile-inotify
  is GPL-3.0 while this tree is BSD — a licence blocker, not a preference. The
  C++-only version that was tried first was removed at the user's request on the
  grounds that it put in C++ what Scheme could do; this does the opposite and is
  smaller for it.
- THREE BUGS FIXED ON THE WAY IN, all in the binding as first drafted:
  (1) it parsed only the FIRST event of a read — a read returns every queued
  event concatenated, so the tail was dropped and a reload silently missed;
  (2) it redefined Guile's own `pointer->procedure`, shadowing the import, so
  anything else in the module wanting the real one got the wrong function (now
  `libc-procedure`, which takes a NAME where Guile's takes a pointer);
  (3) `rassoc` is in neither (guile) nor srfi-1 — compile-lint said so, and the
  two alist lookups are now written out rather than reached for.
- ONE BEHAVIOUR CHANGE, deliberate and worth flagging: the host's "ANY .scm
  beside the config reloads it" heuristic is GONE. It existed only because the
  host could not know what a config loaded. Keeping it alongside the new watcher
  would fire a SECOND reload for every edit to a split config beside
  hyprland.scm — which is the documented arrangement, so the common case. The
  config file itself is still watched by the host (symlink-resolved), and
  everything else a config reads is covered by the watcher, wherever it lives.
- Tests: t-config loads a scratch file from OUTSIDE the config directory, edits
  THAT file, and requires the config to come back — the marker it writes is only
  run because the config re-ran and re-loaded it. VERIFIED TO FAIL: with the
  hl--c-on-readable registration neutered the test reports "did not reload
  (marker=0)", so it is testing the watch rather than passing for another reason.
  t-api asserts the file a config loaded appears in hl-loaded-files (which is how
  the hook is observable at all). 20/20; make check 7/7; api-check reported ONE
  addition, hl-loaded-files, and no removals, and the snapshot was rebaselined.

== COLOURS ARE NUMBERS; strings go through string->color ==
- A colour is now a 0xAARRGGBB INTEGER everywhere in the API — alpha first, the
  packed-ARGB32 layout CHyprColor's uint64_t constructor reads. Scheme has hex
  literals, so a config writes (hl-notify! "hi" 5000 #:color #xffffa500) and
  nothing is parsed. The gsubrs take SCM and convert with colorFromNumber.
- A STRING IS REFUSED by a colour argument, on purpose. Hyprland's config-file
  spellings still work but only through a new, deliberate function:
  string->color (in core, so every module and config reaches it) answers the
  integer or #f. It delegates to Config::ParserUtils::parseColor — the
  compositor's OWN parser, the one the config file, the rule engine, the IPC
  commands and the scripting API all use — so our acceptance set is Hyprland's
  by construction, the same argument as resolveKeycode for keysyms.
- WHAT THIS FIXED. The old schemeColorFromStr accepted bare hex digits
  ("FFA500FF") that Hyprland's parser REJECTS — an invented spelling — and
  refused rgba(...) that Hyprland ACCEPTS: both stricter and more permissive
  than the format it claimed to implement. Worse, the reader returned an
  integer while the setter demanded a string, so
  (hl-notification-color-set! n (hl-notification-color n)) was impossible. The
  parity gap is why rgba(ffa500ff) worked in bindings.lua and failed in
  bindings.scm.
- hl-notify!'s absent colour is #f, not 0: 0 is a legal colour (transparent
  black), so #f is what means "the icon's default".
- THE TESTS ARE MEASURED, NOT GUESSED. Seven spellings pinned against expected
  decimal integers, and the expectations were verified by linking the tree's own
  ParserUtils.cpp.o and printing what the compositor's parser actually answers —
  all eleven rows matched, including the two refusals ("red", "FFA500FF"). The
  load-bearing one is "#00ff00ff" -> #xff00ff00: a hex passthrough would say
  #x00ff00ff, so it fails the moment anyone "simplifies" the string path. Also
  pinned: "#fa5f" (four digits) is #f, since the parser takes 3, 6 or 8 only.
- Tests also cover the round trip that used to be impossible, and that a STRING
  is refused by the setter. t-api had one older call site still passing a string
  ("0x80FF80FF") — the new code caught it, which is the change working.
- Docs: notifications.md gained a Colours section — the alpha-first layout, the
  #xffa500ff trap spelled out, and string->color with its full accepted set.
  CLAUDE.md gained a COLOURS convention.
- 316 gsubrs registered/called (was 315); 20/20 suite; make check 7/7.

== THE MACHINERY COMPILER WAS BROKEN, AND hyprpm HID IT ==
- `make scm-compile` was aborting with a CORE DUMP and hyprpm still reported the
  build as successful, so this user's installed machinery sat at the last good
  copy (00:34) while the plugin updated — which is why the new (hyprscheme
  watch) auto-reload was not live in their session at all.
- THE CAUSE WAS MINE, and the trap is worth knowing. guild compile runs with the
  machinery dir on GUILE_LOAD_PATH (it must — modules resolve each other by name
  from there), and GUILE EVALUATES <load-path>/init.scm AT STARTUP. So compiling
  ANY module evaluates init.scm, which imports everything and runs each module's
  top level. watch.scm called hl--c-on-readable at its top level; that gsubr
  exists only inside the compositor, so a plain guile died with
  "Unbound variable: hl--c-on-readable" -> "Aborted (core dumped)". Verified by
  putting a (display ...) in an init.scm on the load path and watching it print
  during an unrelated module's compile.
- WHY NOTHING CAUGHT IT: scm-compile is NOT part of `make check`, so every lint
  I ran all session was green. `install` and `hyprpm-machinery` both depend on
  it, so both were broken too — and bind-audit, module-audit and compile-lint
  all passed throughout.
- THE FIX: watch.scm's top level now only DEFINES. The fd is opened and the
  arming attempted under a `guard`; outside the compositor it fails harmlessly,
  the fd is closed, and hl--watch-armed? stays #f with the hook inert. The
  kernel's "keep the top level to defines" rule is the same rule, one module
  earlier, and CLAUDE.md now states it generally.
- HONEST LIMIT OF THE GUARD: it makes the arming failure invisible to
  load-check and compile-lint, so a real arming bug would show up only in the
  compositor — where t-config's watcher test covers it (verified to fail with
  the registration neutered).

== ERRORS ARE NOW VISIBLE: a notification at runtime, a banner at load ==
- THE PROBLEM: an error went only to stderr, and the compositor log does not
  carry [scheme] lines in every session (measured: ZERO in a live one), so a
  raising bind thunk looked exactly like a key that does nothing. The scratchpad
  key this session started on had been raising on every press for weeks; the only
  trace was a log line nobody was reading.
- THE SPLIT IS HYPRLAND'S OWN, taken from CConfigManager::addError
  (ConfigManager.cpp:829), which already answers two different questions with two
  different surfaces:
    * a RUNTIME error (in a callback, config already loaded) -> an ordinary
      NOTIFICATION, transient, ICON_WARNING, prefixed "Runtime error in lua:"
      on their side.
    * a CONFIG error (raised while loading) -> the persistent full-width
      ErrorOverlay BANNER, accumulated and capped at ~15 lines with "... more".
  Ours routes the same way: hl--report e WHO -> notification;
  hl--report-config -> ErrorOverlay via a new hl--c-error-overlay gsubr.
- RUNTIME ERRORS ARE DEDUPLICATED PER (WHO, MESSAGE), which is the load-bearing
  part — a broken callback raises on EVERY event, so an unthrottled toast would
  be worse than the silence. Modelled on LuaCaller.cpp's markReported (a
  per-function table of already-reported messages). Ours is hl--reported, keyed
  by the WHO each call site passes: bind, event handler, timer, layout, gesture,
  module reset. A DIFFERENT message from the same callback still gets through
  (asserted).
- All 14 fire trampolines now pass a WHO, named for what the USER would
  recognise ("bind", "event handler", "layout"), not the internal function.
- The watchdog reports through hl--report-watchdog and DOES notify: the desktop
  was frozen for the whole budget. hl--print-exception now renders a plain STRING
  as itself, since that path passes a finished message rather than a condition,
  and ~s-quoting it would have changed a log line t-zzzz-exit matches on.
- NO MAX-RECURSION GUARD, deliberately, at the user's direction: Lua needs one (a
  C lua_State stack), but Scheme recursion is bounded by the VM's own stack and a
  callback re-entering is ordinary, so a depth cap would break correct configs.
  The timeout half IS implemented (already was, as the SIGALRM watchdog).
- THE CONFIG BANNER IS CLEARED BY A SUCCESSFUL LOAD: hl--report-config-ok, called
  by the HOST after evalFile succeeds — the Scheme side cannot know the whole
  config finished, since a config is many files and each load is a separate call.
  It accumulates across failing files, capped at 12 lines like the compositor's
  own, so a config that fails on every form cannot build a banner taller than the
  screen.
- THE NOTIFICATION CALL IS GUARDED AND SILENT ON FAILURE: it runs inside error
  handlers, and a raise there would replace the error being reported with a new
  one. It calls the GSUBR rather than hl-notification-add!, because that name
  lives in (hyprscheme notification) — a FAMILY — and the kernel may not reach
  into one.
- ErrorOverlay reachability VERIFIED before relying on it: nm -DC shows
  ErrorOverlay::overlay(), queueCreate and queueError all exported (T), so the
  plugin links them exactly as it links ParserUtils.
- Tests: t-api fires a deliberately raising bind through hl--bind-fire-rec (the
  same entry the keybind manager calls), asserts a notification appears, that the
  SAME message in the same callback is suppressed, and that a DIFFERENT one is
  not. VERIFIED TO FAIL — with hl--notify-error neutered it reports "a raising
  callback produced NO notification (before=0 after=0)" and both follow-ups.
  t-zzzz-exit then failed on the new deliberate probe messages, which is that
  check working; they are in its allowance list now. 20/20; make check 7/7; 317
  gsubrs registered/called.
- One gotcha hit on the way: `(define (f x #:optional y))` is a SYNTAX ERROR —
  `#:optional` needs define*, and the failure reads as the unhelpful "source
  expression failed to match any pattern". The fix uses a plain rest arg, which
  also avoids a keyword parser on a path called from inside guards. (`take` IS
  available: the kernel imports srfi-1.)

== hl-submap IS GONE: THE SUBMAP IS A NAME ON THE BIND ==

Chris, after walking through how Hyprland actually models submaps: *"get
rid of hl-submap, change hl-bind-add! to be (hl-bind-add! (hl-kbd
"blah") thunk #:submap subma #:submap-reset submap)"*. Recorded in
CLAUDE.md under API conventions.

- WHY IT WAS WRONG, established by reading the compositor rather than the
  docs: a submap is NOT an object. `SBindMetadata::submap` is a
  `std::string` (src/keybinds/Bind.hpp), `CBind::make` copies it out of
  the args struct without looking at it, and `CRegistry::hasSubmap` is an
  `any_of` over the flat bind vector comparing strings. There is no
  submap-creation call anywhere in src/keybinds/, and
  `CKeybindManager`'s entire submap API is ONE GETTER (`currentSubmap`).
  **A submap exists because binds carry its name**, which is also why
  entering one no bind carries is refused.
- THE OLD hl-submap made the name AMBIENT instead of an argument: a
  dynamic-wind that set `g_regSubmap` while a thunk ran, so every bind
  created inside inherited whatever name was in force. That is how the
  .conf format works (`submap = resize` is a parser-state directive) and
  how the Lua binding does it, but it meant NO language could say "this
  ONE bind goes in resize" — and the .conf heritage is why the verb
  "create a submap" read as true when nothing was ever created.
- DELETED: `hl-submap`, `hl--c-get-submap-ctx`, `hl--c-set-submap-ctx`,
  and both C++ globals. `hl-bind-add!` gained `#:submap` and
  `#:submap-reset`; `hlSchemeBind` takes two more `const char*` and writes
  them straight into the metadata. `""` is the default map, so every
  existing bind keeps its behaviour — the trampoline is variadic, so the
  arity change needed no C++ plumbing either.
- THE LUA EQUIVALENT is `hl.define_submap` (LuaBindingsToplevel.cpp:234),
  the direct ancestor of what was deleted. Worth knowing: `hl.bind` has NO
  submap option there either — the name comes from
  `mgr->m_currentSubmap`. Our API is now STRICTLY MORE EXPRESSIVE than
  the Lua one, which is a first.
- `define-key!` (emacs-keymaps) needed no design change — it always
  wanted a per-bind name — but its three internal `hl-submap` wrappers
  became `#:submap` arguments. **Its post-action EXIT deliberately stays
  in Scheme** rather than becoming `#:submap-reset`: the compositor
  applies a reset inside `invokeBind` AFTER the thunk, and this harness
  fires a bind by calling the thunk (`hl--bind-fire-rec`), so two real
  tests in t-keydesc.sh assert the post-action submap that way. Moving it
  to C++ would have quietly made them tests that cannot fail — which is
  exactly the trap CLAUDE.md calls out. `#:submap-reset` is public for
  configs that want the declarative form.
- THE BUG FOUND ON THE WAY, and it is the kind this tree tests for:
  `hl-bind-add!`'s "you gave me a sequence" error told the user to use
  **`hl-bind-keys!` — a function that has never existed** (not in
  bind.scm, emacs-keymaps.scm or API.snapshot). The real one is
  `global-set-key!`. Worse, `t-keydesc.sh` PINNED that wording, so the
  test was checking the bug in rather than out. Fixed both: the message
  names `global-set-key!`, and the test now also asserts the named
  function is a procedure.
- TESTS: t-api's submap block was rewritten around `#:submap`, and adds a
  case for a submap no bind carries (refused, `#t` from
  `not (hl-submap-activate! "…")`) plus one that reads the `submap` FIELD
  back through `hyprctl binds` — an external check, not a Scheme accessor
  agreeing with itself. **`#:submap-reset` is deliberately NOT asserted**,

  thunk, hyprctl exposes no such field, and a synthetic keypress is
  dropped before dispatch (t-keydeliver.sh documents that), so any
  assertion here would be one the harness cannot see. That is stated
  rather than papered over.
- DOCS: submaps.md REWRITTEN (it taught the wrapper, described nesting as
  a runtime hierarchy that does not exist, and claimed submaps "can be
  nested"); binds.md gained the two options; code-snippets.md's group
  submap is now a `map-g` helper taking the map name; examples/hyprland.scm

  hl-submap!/hl-key-description layer, which was documented NOWHERE in

== BIND FLAGS: a values enum, spelled the way Bind.hpp spells them ==
- `bind-flag-enum` (in (hyprscheme core), PUBLIC) names the 16
  BIND_FLAG_* bits: locked release repeat long-press non-consuming
  auto-consuming transparent ignore-mods dont-inhibit click drag
  submap-universal allow-input-capture device-inclusive catch-all mouse.
  Declared in Bind.hpp's ORDER and written `(ash 1 N)` beside its
  `(1 << N)`, so the two tables can be compared line by line — which is
  the whole point: the day they stop matching is the day an option
  silently lands on the wrong flag.
- hl--bind-flags now combines them with enum-value + logior instead of
  adding decimal literals. The three DERIVED bits (click/drag imply
  release; #:devices implies device-inclusive unless opted out; the key
  name "catchall" implies catch-all) are each named at the point they are
  set and sit beside the line of Bind.hpp that does the same thing.
- BUG FOUND WHILE DOING THIS, and the reason logior is load-bearing
  rather than tidy: the old code combined the bits with `+`, and click
  and drag EACH imply RELEASE — so `(hl--bind-flags #:click #t
  #:release #t)` added 2+2 = 4 = BIND_FLAG_REPEAT. Asking to bind a click
  silently armed autorepeat. Measured: the call answered 516 and
  `(logand 516 4)` was 4. logior cannot collide however the options
  overlap.
- core may now import (hyprscheme enums) — core is a leaf like enums, so
  this is leaf-to-leaf and not core reaching into a family. module-audit's
  CORE clause updated (and its docstring says why). core's #:export gained
  bind-flag-enum.
- TESTS (t-api.sh): the individual values against Bind.hpp's shifts
  (locked 1 … catch-all 16384, mouse 32768, ignore-mods 128), the table's
  LENGTH (16 — a bit added upstream and not here is an option that cannot
  be expressed), and the combination the old `+` got wrong. All three
  verified to fail on the old code: with `+` restored the probe reports
  `click+release = 516 want 514` and `logand 4 = 4 want 0`.
- RULES written into CLAUDE.md, as Chris asked, in a new "COPIED
  CONSTANTS — the original's FORM, and a NAME for the set" section before
  ENUMS: (a) a value copied from Hyprland is written the way Hyprland
  writes it, because a copied table has to be diffable by eye — and the
  spelling follows the ORIGINAL, not the tree (inotify.scm keeps padded
  hex because <sys/inotify.h> lists hex); (b) where the copied set is a
  set, NAME it — a values enum when the API speaks the values; and for a

== KEYMAPS: hl-keymap, and define-keymap for a top-level map ==

== THE EMACS LAYER ONTO KEYMAPS: define-key! takes an object ==
PASS 3 of 3.
- BREAKING: define-key!'s first argument is a KEYMAP, not a submap NAME.
  A submap is a name stamped on the binds that carry it; the keymap is
  what HOLDS them, so it is what gets passed, and the name comes from
  the keymap's own `submap` field. A string is REFUSED BY NAME — the
  refusal names hl-make-keymap — rather than falling through to a
  record-accessor error several calls later. global-set-key! now binds
  into `global-map`, the exported keymap whose submap is "", so the
  default map is readable and drivable like any other.
- THE THREE MODULE-LEVEL HASHTABLES ARE GONE. hl--submaps-made became
  the keymap's own `children` alist (it is the assq the proposal asked
  for: submap name -> sub-keymap), and hl--exit-bound / hl--catchall-bound
  became a `marks` set on the keymap. Both live on the keymap record.
  - A MARK, NOT A LOOK FOR A BIND. The obvious spelling — "does this map
    already have an s-G bind?" — is WRONG: a config may bind s-G itself,
    so it would answer yes for a map we never gave an exit to, and the
    map would be left without one. Hence marks.

== IF A NOTIFICATION ARRIVES, IT IS DELIVERED: three events were dropping payloads ==
- THE RULE, from Chris, and it is a rule rather than a case-by-case judgement:
  "as far as I'm concerned, if a notification arrives there is never an excuse
  to not pass it on". A missing object crosses the boundary as #f and the
  handler is still CALLED. A dropped event is not one fewer call — it is a
  state change the handler never learns about, which is strictly worse than a
  call it has to null-check.
- WHAT WAS WRONG, found by asking which C++ handlers guard their payload rather
  than assuming any particular one was fine. The tell was `emit(m_self.lock())`
  (an expired weak ref locks to null) as against an explicit `nullptr`, and the
  three real cases were:
  - window.active: FocusState.cpp:148 emits `nullptr` when focus is CLEARED,
    and our handler required a window, so the one event that says "nothing is
    focused any more" was the one we dropped. This is the bug Chris reported.
  - window.move_to_workspace: the C++ captured the workspace and passed only
    the window, so a handler could hear "it moved" and never "where to".
  - window.destroy: the listener delivered NO argument at all.
  Also fixed the same class where it was reachable: workspace.created (null
  workspace), minimize (now propagates #f), and both layer listeners via a new
  fireSchemeStrOrNull. fireSchemeWinWs / fireSchemeWinRef in cpp/Event.cpp and
  hl--fire-win-ws-rec in the kernel are the new paths; each is a separate
  function rather than a branch inside the existing one, because the arity of
  the Scheme call is fixed per entry point.
- EVERY CASE IS ASSERTED BY t-events.sh, and each new assertion was verified to
  fail before its fix — destroy by asserting the argument is a HANDLE (a
  zero-argument handler leaves the state unset, so the test reports that rather
  than passing vacuously), move_to_workspace by asserting the workspace NAME
  arrives, and active by asserting #f. The three blocks carry the reasoning in
  comments because the failure mode of each is invisible.
- THE window.active TEST TOOK THREE ATTEMPTS, and both intermediate reasons are
  worth keeping:
  - It failed only under the full suite and passed alone, which I first wrote
    off as ordering. It was: the block that ran before it moved a window to
    workspace "9", carried the session there and closed the window, so the
    session was ALREADY unfocused when the test asked for "no focus".
    **Hyprland emits window.active only when focus CHANGES** — FocusState.cpp
    returns early on `if (m_focusWindow.expired() && !pWindow)` — so focusing an
    empty workspace from a state of no focus emits nothing at all. The test now
    forces the transition by focusing a window first and asserts THAT too, so a
    silently-dead handler cannot be read as a passing clear.
  - The clear then still did not arrive, and the workspace was still "1": a BARE
    non-numeric name is not a way to reach a workspace that does not exist yet.
    Resolver.cpp's fallback is `targetFor(query().input(in).run())`, a lookup

    creates is `name:`. The block now uses `"name:ev-empty-ws"`, and a failure
    message prints which workspace it actually ended up on, because "the event
    did not fire" and "the setup never happened" are indistinguishable without
    it. It also records the WHOLE delivery sequence rather than the last value,
    which is what separated "the clear never fired" from "the clear fired and
    something re-focused".
- The workspace this file starts on is captured BEFORE anything moves windows,

  9, so "restoring" restored 9 and left the rest of the suite there.

== KEYMAPS FOLLOW THE FOCUSED WINDOW'S TAGS ==
- NEW: hl-keymap-attach-to-tag!, Chris's proposal. (hl-keymap-attach-to-tag!
  KEYMAP TAG) arms KEYMAP exactly while the focused window carries TAG and
  disarms it otherwise, so a mode can belong to an APPLICATION instead of to a
  key you press. The registry (tag -> keymaps) and the window.active listener
  both live in (hyprscheme emacs-keymaps), because that is the module the whole
  keymap layer lives in — it is a composer, so reaching (hyprscheme window) for
  hl-window-tags / hl-active-window is allowed and is checked: module-audit's
  can-it-see-everything-it-calls rule covers the new import.
- THE REGISTRY IS THE DESIGN, not bookkeeping. Only keymaps an attach put under
  this policy are ever armed or disarmed by it, so re-evaluating on every focus
  change cannot touch a keymap the config armed itself — global-map included.
  One attached keymap cannot silently disarm another; the listener's reach is
  exactly what it owns.
- THE LISTENER IS INSTALLED ON THE FIRST ATTACH and not before, and `reset`
  FORGETS its handle rather than keeping it. That is not tidiness: on reload the
  host tears every event handler down and the new generation re-registers, so a
  guard still holding the old record would believe the listener was installed,
  never install another, and freeze the registry at whatever the first focus
  change made it. The opposite answer to the GC hook, which is installed once
  for the process and must NOT be reinstalled — same class of trap, opposite
  sign.
- THE ATTACH RE-EVALUATES ONCE ITSELF, so a config that attaches during load is
  right about the window already focused instead of waiting for a focus change
  that may never come. Pinned by a test that DISARMS the keymap by hand and then
  attaches with no event in between — without that disarm the assertion would
  pass whatever attach did, because a fresh keymap is enabled at birth.
- THE KEYMAP NOW KNOWS WHAT IT WAS LAST TOLD: a boolean `enabled` field, read by
  hl-keymap-enabled?, written by hl-keymap-enable!/disable! and by nothing else.
  hl-make-keymap makes one enabled, define-keymap's is disabled (it already
  called hl-keymap-disable!, which now records it). Documented as what the keymap
  was TOLD, not a probe of the compositor — a single bind can still be disarmed
  with hl-bind-enabled-set! and the keymap would not know. It is what makes the
  unconditional re-evaluation above cheap enough to not need a memory of what was
  armed last time.
- TESTS, and both halves of the mechanism were verified to fail SEPARATELY,
  because one neutering would have hidden the other:
  - with the tag matcher (`hl--tag-apply`) made a no-op, three assertions fail —
    the attach-time arm, the binds following the flag, and the focus-driven arm;
  - with the LISTENER never installed, a different two fail — the focus-driven
    disarm and the focus-driven arm — while the attach-time assertion still
    PASSES, which is exactly the distinction being drawn.
  The test keeps its keymap in hl-state across the separate $SCHEME evals and
  deliberately never unbinds its bind: the keymap stays in the registry for the
  rest of the session, so a later focus change will arm it again, and arming an
  UNBOUND record is not something to discover from a log line in t-zzzz-exit.
  Focus transitions are forced with a focus-away-and-back, since window.active
  fires only on a change.

== ATTACHING TAKES A CONDITION, NOT A TAG — the general form, Chris's design ==
- NEW: hl-keymap-attach-to-window-condition! (KEYMAP THUNK), where THUNK takes
  the focused window — a handle, or #f when nothing is focused — and answers
  whether the keymap should be armed. hl-keymap-attach-to-tag! is now written IN
  TERMS of it: the tag call is the same machinery with the condition written for
  you, so there is one mechanism and not two.
- WHY IT HAD TO GENERALISE, and it was not a preference. A tag is a string a
  window either has or has not, so the condition a real config wants is usually
  NOT a membership test. Chris's own keymap is armed UNLESS the app speaks emacs
  — a NEGATION, and there is no tag you can be a member of for it. The tag form
  could not express it, and the negation is not an edge case: it is most of the
  policy.
- AND IT KILLED THE OTHER OBSTACLE. ekeys mode arms those same keys even in a
  terminal, which is a MODE FLAG and not a window property at all — no tag
  vocabulary could ever reach it, and it cannot be handled in the handler either,
  because a DISARMED bind never fires and so never reaches one. A lambda closes
  over the flag and reads it.
- THE COST OF READING A FLAG IS STALENESS, and it is paid explicitly rather than
  hidden: a condition is evaluated when the focused window CHANGES, so a mode
  flag flipping is invisible to the registry. Hence NEW: hl-keymaps-recheck! —
  re-evaluate every attached keymap against the window focused right now. The
  mode setters call it. The alternative was re-running every condition on every
  key press, which is the cost the whole design exists to avoid. t-keymap.sh
  states the staleness AS A TEST — flip the flag, assert still disarmed, recheck,
  assert armed — and was verified to fail with hl-keymaps-recheck! neutered.
- ONE CONDITION PER KEYMAP, and attaching again REPLACES it. A lambda can say
  "this tag OR that tag" itself, so the two readings cannot be confused; the test
  that proves the replace is a recheck after re-attaching an always-#f condition
  over an always-#t one — with both retained the keymap would re-arm.
- reset clears the registry and forgets the listener handle, unchanged, and the
  listener is still installed on the first attach only.
- WHAT EKEYS MODE IS, settled by Chris, because the old code had answered it
  three different ways at once: ekeys is a mode for driving HYPRLAND with
  emacs-shaped keys — C-x <left> stepping through a tab group the way it steps
  through emacs' tab line — even while sitting in emacs (or a terminal, where the
  shell speaks emacs too). IT NEVER CHANGES WHAT THE APP RECEIVES. The mode only
  ever ARMS keys that were disarmed, and every key it arms performs a Hyprland
  action.
- THE OLD CODE CONTRADICTED THAT THREE TIMES OVER, which is why it read as
  incoherent: under ekeys with a terminal focused, the movement translations were
  armed and then the handler re-tested the window and sent THE SAME KEY back (a
  capture-and-re-inject that changed nothing), C-r did the same, and C-k sent
  S-End + Delete — DIFFERENT KEYS to the app, which is the one thing the mode must
  never do. The predicate that fed all of it was one shared not-emacs-window?,
  which is how translation policy and mode policy came to be the same boolean.
- SO THE TWO ARE SEPARATE KEYMAPS NOW, differing by exactly one term:
  emacs-simulation-map (the translations) is armed only OUTSIDE an app that
  speaks emacs; ekeys-map (the Hyprland actions) is armed there too, while ekeys
  mode is on. That IS the mode, stated in one line, and it is why no handler
  needs to re-test anything: being armed is the decision.
- EVERY HANDLER RE-TEST IS DELETED — emacs-simulate, C-k, C-r, the C-x prefix,
  M-% and C-l. They existed to undo an arming that should never have happened,
  and each was justified in the file as a "race guard" for the window between a
  key press and a focus change re-arming the bind. THERE IS NO SUCH WINDOW:
  window.active is emitted synchronously inside the focus change, on the
  compositor's thread, before the next key can be dispatched. emacs-simulate no
  longer even takes the emacs chord, since the one thing it used it for was
  sending it back.
- BINDINGS2.SCM REWRITTEN IN FULL, and the old machinery is GONE from it:
  emacs-translation, bind-app-translation, app-translations,
  refresh-app-translations, the window.active listener they needed, the
  hand-rolled re-evaluate in every mode setter, the end-of-file initial pass, and
  every predicate that existed only to feed them. Nineteen top-level registrations
  became nineteen clauses of emacs-simulation-map; C-k is a clause of it too (a
  translation like the rest); ekeys-map is the C-x prefix, one clause and the door
  new ekeys keys come in by; C-r is find-backward-map (the simulation's condition
  plus LibreOffice); and set-mark-map uses the simulation's condition while
  cancel-mark-map's is the mark flag alone, ignoring the window entirely — which
  is a thing a lambda says and a tag cannot.
- TWO MAPS FOR THE C-x CHORDS, for one mechanical reason, and the split is
  load-bearing rather than tidy: a keymap has ONE submap and these binds live in
  two. The key that ENTERS is in the default map and carries the ekeys condition;
  the chords are in "C-x" and carry NO CONDITION, because they are already gated
  by the submap being current — and because a DISARMED bind does not match at all,
  so if the chords went down while you were inside the submap the catchall that
  abandons a mistyped chord would go with them and there would be no way out but a
  reload. Being in a submap is a state the config must always be able to leave.
- VERIFIED against a truth table in a nested compositor, because arming is
  invisible until a key is pressed (columns: simulation, C-r, C-SPC, C-g, ekeys):
  plain (#t #t #t #f #t), terminal (#f #f #f #f #f), terminal + ekeys
  (#f #f #f #f #t), terminal + mark (#f #f #f #t #f), both off (#f #f #f #f #f),
  libreoffice (#t #f #t #f #t). THE THIRD ROW IS THE WHOLE DESIGN: ekeys armed,
  simulation NOT — the mode takes the C-x chords in a terminal and translates
  nothing. Tags applied by a real window rule, so "terminal*" is what is matched.
  Zero config errors, zero [scheme] error lines. Each attach evaluates the WHOLE
  registry when it is made, so the last attach is also the initial pass and the
  ordering bug the old copy had cannot recur.
- FOUND BY READING, after Chris said so and he was right: nineteen lines read
  (define-key! c-x-map(hl-kbd "C-f") because my own replace_all ate the space.
  VALID SCHEME — "(" is a delimiter — so every test passed and every probe agreed;
  only looking at the file shows it. That is the case for reading the diff rather

== THE THREE GROUP LOCKS, named as one family, and the missing one built ==
- ADDED: hl-group-lock-set! — lock/unlock ONE group by its HANDLE, with the same

== define-keymap TOOK SEQUENCES; the banner NAMES THE FAILURE ==

Two things Chris asked for, and both had the same shape: the machinery could do
something the code did not expose, and the error you got instead named nothing.

--- 1. define-keymap could not bind a SEQUENCE, which is what it is for ---

Chris's bindings.scm is built out of `C-x` chords — emacs' own shape — and it
could not be written with the form meant for that shape:

  (define-keymap ekeys-map ""
    ((hl-kbd "C-x C-s") (lambda () ...)))     ; refused

define-keymap bound each clause with hl-make-bind, which takes ONE CHORD, so any
two-key clause died with "tokens must be a list of key-name strings ... it is a
SEQUENCE". The message was accurate and useless: it named a workaround
(global-set-key!) rather than the fact that the form you are already using is the
one that should work.

IT NOW GOES THROUGH define-key!, which WALKS the sequence: builds the "C-x"
prefix submap, binds the key that enters it, and gives that submap its own s-G
and catchall. So a chord and a sequence are written identically and the config
never does prefix bookkeeping. The disarm runs LAST, after the last clause, so
it covers the prefix binds too.

THAT FORCED A MOVE. define-key! is (hyprscheme emacs-keymaps)'s, and the submap
names come from hl--expand -> hl-key-description, that module's own key layer —
so define-keymap cannot live in (hyprscheme bind) any more: a FAMILY imports only
the kernel and core, and module-audit enforces it. bind.scm keeps a note saying
where it went and why; nothing else moved, because a keymap is still a bundle of
binds, which bind.scm owns.

TWO MORE SHAPE CHANGES, both Chris's call:

  - `#:submap` is a KEYWORD defaulting to "", so a top-level map omits it:
      (define-keymap browser-map (((hl-kbd "C-l") (lambda () (reload)))))
    It was a positional argument, which meant writing "" every time for the
    common case.
  - THE CLAUSES ARE ONE LIST, in an extra pair of parens. That is what lets a
    config hold them in a variable, splice two sets, or build them in a loop —
    none of which a varargs form can do, since only literal forms may appear
    there.

define-key! ALSO FORWARDS BIND OPTIONS now (#:description, #:repeat, ...), to the
bind the sequence ENDS on. It absorbs #:top-level itself, so the forwarding has
to strip that one keyword — and the spelling that works is
`#:key (top-level #t) #:allow-other-keys #:rest opts`, NOT `#:key K #:rest R`:
measured on 3.0.11 the latter RAISES on any unrecognised keyword, while with
#:allow-other-keys present it captures, and then re-captures the recognised ones
too, which is why the filter exists. (CLAUDE.md's "#:key #:rest, full stop" rule
is about the common case; this is the case it does not cover.)

- TESTED: t-keymap.sh gained seven assertions — a sequence's action landing in
  the "C-x" submap, exactly ONE bind reaching the top map, a chord and a sequence
  coexisting, the disarm reaching the prefix bind, #:submap naming the map, and
  an option arriving on the bind. run.sh 21/21.
- Docs: keymaps.md and emacs-keymaps.md rewritten for the new shape; every
  define-keymap example in the wiki updated (doc-exercise evaluates them all, so
  a stale one fails the suite). API.snapshot unchanged in kind — the name moved
  module, which api-check reports as an addition, and additions pass by design.

--- 2. An error now names the FILE and states the ARITY ---

Chris, verbatim: "when my bindings.scm has an error ... 'wrong number of
arguments to procedure at ice-9/eval.scm 330.13' ... that error isn't very
helpful, and is it possible to get a full stack trace or something". It sent him
through a 900-line file by hand, and the banner — the one surface built to tell
him — named nothing.

TWO THINGS WERE MISSING, and both are knowable at the point of the raise:

  - THE COUNT. `wrong-number-of-args` carries the PROCEDURE in its irritants,
    and procedure-arguments answers its lambda list as data — so the message can
    say what the callee takes: "Wrong number of arguments (the procedure takes 0
    arguments)". For the real bug — a `(lambda ()` written where a `(lambda (w)
    ...)` was wanted — the count IS the diagnosis.
    (procedure-arguments needs (ice-9 session), which the kernel did not import.
    The first version answered #f on any raise, which is how a reporter must
    behave and also how it hid its own bug; it now LOGS a failure in itself
    rather than degrading silently. The test for the count is what caught it.)
  - WHERE. A backtrace exists only BEFORE the unwind — measured: a post-unwind
    guard sees its own frames and nothing else. So hl--load-config and hl-load
    each stash one from a pre-unwind handler and RE-RAISE, leaving the error
    handling itself untouched. Each recorded error now carries its file
    ("...  [cfg-arity-broken.scm (loaded)]"), and the log gets the same plus a
    filtered frame list.

THE FRAMES THAT MATTER ARE NOT THE ONES WITH A FILE, which is the non-obvious
part and cost two wrong versions: a file loaded form-by-form reports NO source
at all (frame-source is #f), so a renderer reading only frame-source printed an
empty backtrace. What identifies a config's frame is a `primitive-load` frame
whose ARGUMENT is the path — measured for a nested load the order is inner then
outer, so the FIRST is the file to open. eval.scm/boot-9.scm/psyntax.scm are
dropped, because a wall of evaluator frames is what makes a raw backtrace
unreadable.

- TESTED and verified to fail BOTH WAYS, independently: t-config.sh loads a file
  whose helper takes no arguments and is called with one, then asserts the banner
  states "0 argument" and names the file. Neutering only the count fails the
  first; neutering only the file fails the second; each was run and each failed
  the right assertion alone. t-zzzz-exit's allowance list gained the arity line
  (it appears twice — the failing load, and the reload the watcher triggers).
- Docs: core.md's errors section now says what an error names.
- tools/form-trace.scm (untracked scratch, kept for now) was the bisector this
  was diagnosed with; making it trustworthy was most of the work, and its two
  traps are recorded in it: a stub must answer a NUMBER where the machinery
  compares numerically (0 for a status code, 1 for a magnitude — answering #f
  FAKED two failures that were not the config's), and a comparison can be
  THROUGH A PARAMETER, so a gsubr passed as a value to a helper that tests its
  own argument is invisible to a scan of call sites (core.scm's
  hl--window-rule-mk).
