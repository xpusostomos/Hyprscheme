== THE LOADER (init.scm owns the module list) ==
- init.scm is the ONLY list of modules, and the ONLY thing the host
  loads. Host.cpp names no module at all: it creates the kernel and
  registers the gsubrs, makes the generation, makes it CURRENT, then
  one evalFile(init.scm) — so init.scm's `use-modules` ARE the
  generation's environment, stdlib included. The 23-line useModule()
  list that duplicated init.scm's and could drift from it is GONE.
- init.scm's `in?` was a load masquerading as a probe. `resolve-module`'s
  second POSITIONAL arg is `autoload` (default #t) and `#:ensure` is a
  separate switch, so `(resolve-module name #:ensure #f)` still LOADED
  the file and answered "already in" for a module never loaded. Every
  module's body therefore ran TWICE on generation 1, and the macro's
  `use-modules` branch was dead code that never once executed.
- The probe is now `(resolve-module name #f #:ensure #f)` AND a
  `module-filename` check. Autoload off is not enough on its own: a
  module can exist with no file behind it. `(hyprscheme)` is the parent
  of every `(hyprscheme X)`, so the tree grows it as a directory module
  as soon as the first family is defined, and `reload-module` on it
  fails ("unknown file name for module"). Verified the hard way —
  without the check, the last line of init.scm dies on gen 1.
- The macro reloads if present and then ALWAYS imports: `reload-module`
  does not import, so gen 2+ would otherwise get nothing. Guile's own
  modules (the five stdlib ones) use plain `use-modules` — `reload-module`
  on one is an error, not a refresh.
- The umbrella is LOADED but not IMPORTED, deliberately: importing it
  would make a config's environment depend on the re-export list, so a
  public name added to a family but not yet to the umbrella would go
  missing from configs.
- tests/t-generation.sh pins it, asserting the generation's own USE-LIST
  rather than that a call works. Guile resolves names through a used
  module's use-list transitively, so with the old order the generation
  still REACHES everything and the whole rest of the suite passes — only
  the use-list shows it. Verified to fail by restoring the old order
  (names all 18 missing modules).
- tools/load-check.scm mirrors the new order: the generation is made
  before init.scm and is the module init.scm is read in.
- FIVE dead hl:: helpers removed from Guile.hpp/Guile.cpp, with the
  private thunks and includes that only they used (callThunk0,
  moduleCall1Thunk, ModuleCall, <sstream>, <vector>):
    useModule   — orphaned by this work: the import list moved into
                  init.scm and no caller was left
    exportAll   — the kernel exports by #:export now, not module-export-all!
    resolveModule — a byte-for-byte duplicate of makeModule, which superseded it
    loadModule  — init.scm loads modules by name
    call0       — nothing makes a 0-arg contained call
  The last four were already dead before this work. Kept: the
  define-module-expands-in-the-CURRENT-module insight, which is live
  (load-check.scm implements it) and now lives in CLAUDE.md with
  loadModule marked dead rather than as a claim about live code.
- tools/bind-audit.py now REPORTS dead helper declarations in Guile.hpp,
  so this class cannot silently re-accumulate. Verified to fail: adding
  `SCM nothingCallsThis(const char*)` trips it, exit 1, naming the
  offender. The check is exact (hl::-qualified mentions only) precisely
  because a bare-name search matches same-named members across the tree
  and would be disabled as noisy.
- makeModule's comment corrected: it claimed `#:ensure` is what makes it
  create on a miss. It is the C entry point scm_c_resolve_module, which
  has no such argument — it creates on a miss AND autoloads.

== ENUMS: a name for a set of values ==
- NEW MODULE (hyprscheme enums) — a LEAF like core (imports the kernel
  only, no compositor knowledge), so every family may import it.
  module-audit's rule is now stated around a SHARED set (kernel, core,
  enums) rather than "kernel and core".
- The machinery: <enum-values> (make-record-type) carrying BOTH an ass
  list symbol->integer and an rnrs enum over the same symbols.
  make-enum-values, define-enum-values (sugar), enum-values?,
  enum-value (takes EITHER spelling, returns the integer — so an API
  function accepts a symbol or an integer with no conversion code of its
  own, and a value outside the set is an ERROR naming the set),
  enum-symbol (the inverse; what a getter returns),
  enum-values->enum (the rnrs enum, for the whole (rnrs enums) toolkit).
- The two numberings are INDEPENDENT and both kept: rnrs numbers members
  0..n-1 in declaration order, the API integers are the compositor's
  (fullscreen-mode is -1/0/1/2). Pinned by a test ('keep has rnrs index
  0 but value -1).
- The error names the set in the CALLER'S OWN CURRENCY: a bad symbol is
  answered with the symbols, a bad integer with the integers.
- (rnrs enums) is now imported into the generation (init.scm) — without
  it enum-values->enum returned an inert object and "you also have the
  rnrs toolkit" was false.
- RULE written into CLAUDE.md ("API conventions -> ENUMS"): a function
  taking or returning one value from a fixed set speaks in symbols and
  the set is a named enum. No bare integers, no strings.
- Enums shipped: fullscreen-mode (keep none maximized fullscreen),
  fullscreen-handler (none default layout scrolling).
- tests/t-enums.sh. Everything wired into the tools that have their own
  module lists: compile-lint, load-check, doc-exercise.

== FULLSCREEN: modes as symbols, Lua's three actions ==
- hl-window-fullscreen and the NEW hl-window-fullscreen-client return a
  MODE SYMBOL ('none/'maximized/'fullscreen), and
  hl-window-fullscreen-handler returns a handler symbol. All three take
  #f for the focused window (the mode getter used windowOf, so it raised
  on #f while its maximized? partner accepted it).
- hl-window-fullscreen-set! is now the Lua shape: #:mode
  ('fullscreen default | 'maximized), #:action ('toggle default | 'set |
  'unset), #:layout-aware (#t default, the dispatcher's own). 'set and
  'unset are IDEMPOTENT — no-ops when already as asked — which is what
  stops "unset fullscreen" on a maximized window from clearing maximized.
  (The old #:on? #f wrote FSMODE_NONE, wiping whichever mode was set.)
- hl-window-fullscreen-sync! takes mode SYMBOLS too, 'keep meaning
  "leave this side alone" — still the only way to set the client side, and
  now the documented way to fullscreen a window WITHOUT telling the app.
- hl-window-maximized-set! REMOVED (redundant under #:mode; Lua has no
  second dispatcher). hl-window-maximized? stays.
- C++: new gsubr hl--c-window-fullscreen-client; the toggle gsubr gained a
  layoutAware argument (it hardcoded false, so OUR toggle could not be
  layout-aware while Lua's can); hl--c-window-fullscreen-set REMOVED — the
  rewritten setter uses only the toggle, exactly as Lua's does, and
  bind-audit flagged it dead.
- CORRECTION to an earlier claim of mine: the client side IS told by
  default. `syncFullscreen` (a per-window property, DEFINE_PROP default
  TRUE) makes setFullscreenMode sync client to internal when client is
  absent — so the 3-arg DOES reach the app unless sync_fullscreen is off.
  Caught by a test I wrote asserting the opposite; the docstrings and the
  wiki were wrong and are fixed.

== THE BOUNDARY: bools, symbols, and one decision that was in the wrong place ==
- Arg<bool> added to Bindings.hpp: a C++ bool parameter takes a Scheme
  BOOLEAN by truthiness (scm_is_true). #t is a distinct immediate, not a
  number, so Arg<int> refused it outright — "argument 3 is not an
  integer" — and that is why 19 gsubrs had `int` params with call sites
  writing (if x 1 0). All 19 converted to `bool` + the conversion
  dropped. TRAP: 0 is TRUTHY, so a site left passing (if x 1 0) would
  invert.
- Arg<const char*> takes a SYMBOL as well as a string. A name-ish
  argument (config key, tag, prop) is what Scheme has as a symbol, and
  requiring symbol->string at the call site was 40 conversions. Numbers
  are deliberately NOT accepted — a number means a name only in the
  workspace/monitor resolvers. hl--str went from 40 call sites to 5
  consumers; hl--dir deleted.
- RULE, in CLAUDE.md ("THE BOUNDARY"): a gsubr mirrors the C/C++ call it
  exposes — same shape, just enough to be a sensible Scheme call. Policy
  lives in Scheme. Two violations were real:
  - hl--c-window-fullscreen-toggle hand-rolled an isFullscreen test the
    compositor's own action already does, and threw away an answer
    Scheme had already read. Now hl--c-window-fullscreen-set mirrors
    setFullscreenMode, which SETS.
  - hlCurveAdd(name, int type, a,b,c,d) invented a type argument
    Hyprland does not have — it has TWO calls, addBezierWithName and
    addSpringWithName, and the curve type is WHICH FUNCTION YOU CALL.
    Split into hl--c-bezier-curve-add / hl--c-spring-curve-add, and the
    Scheme API into hl-bezier-curve-add! / hl-spring-curve-add! (the
    variadic . vals and its zero-padding are gone with it).

== hl-load-config reports a load that FAILED (not just a missing file) ==
- hl--load returned #t WHETHER OR NOT the load worked — the guard printed
  the error and then fell through to #t, so a caller could not tell. That
  is how "the config loads but set-mark is unbound" was possible: the
  file died at its 300th form and hl-load-config handed back a path as
  if it had worked. It now returns #f when the guard fires; `load` itself
  still returns #t (Guile's own does, and a config calling it is not
  expected to check).
- hl-load-config raises a DIFFERENT notification for the two failures,
  which are worth telling apart: "config not found: NAME" for a file that
  is not there, and "config failed to load: PATH" for one that raised.
  A missing file is usually a typo; a file that raised has ALREADY
  DEFINED SOME OF ITSELF, so the config is half-applied — the state that
  is hard to diagnose, and the one the notification exists for.
- Tests in t-api.sh, verified to fail: reverting hl--load to answer #t
  always makes the notification assertion fail. t-zzzz-exit's
  allowed-error list gained the error t-api now provokes on purpose.
- Wiki (scheme-utilities.md) and the docstrings say both cases.

== SENT KEYS WERE RESOLVED AS KEYSYMS, NOT KEYCODES (the C-f bug, found) ==
- THE BUG Chris reported as "the key bindings that are mapped to work in
  the browser don't work": hlSchemeSendShortcut and hlSchemeSendKeyState
  resolved the key with xkb_keysym_from_name and handed the KEYSYM to
  Config::Actions::pass. pass() forwards its key straight to
  sendKeyboardKey as `key - 8` — an XKB/evdev KEYCODE, the units of the
  keybind manager's m_lastCode. The two numberings are unrelated, so
  every sent key was the wrong number: "f" sent 94 (not f), and the
  NAMED keys — Right/Left/Next/Prior, i.e. the payload of every chord
  Chris named (C-f, C-b, C-v, M-v) — resolved to ~0xff00, far outside
  the keycode range, and were DROPPED silently. Nothing raised because
  pass() never validates its keycode: actionResult answered 0 and the
  wrappers answered #t.
- WHY IT SURVIVED THE SUITE, the lesson worth keeping: t-crashdir
  asserted that (hl-window-send-shortcut! ...) ANSWERS #t. It did, while
  sending garbage. An assertion on a RETURN VALUE cannot see a wrong
  PAYLOAD. This bug was three weeks old (git blame: 685c20b, 2026-09-26)
  and every lint was green throughout.
- THE FIX: both gsubrs resolve through Keybinds::resolver()->
  resolveKeycode(), exactly as the scripting API's own dispatchers do
  (LuaBindingsDispatchers dsp_sendShortcut/dsp_sendKeyState). It is a
  conversion, not a policy — the boundary is the one place allowed to
  know both spellings. Two side effects: Hyprland's own tokens
  ("code:28", "mouse:272") now work where they were previously refused,
  and a keysym that is not on the LOADED KEYMAP (Cyrillic_a, Arabic_alef
  under `us`) is refused with an error instead of being sent as
  nonsense.
- Query.cpp:142 looks identical but is CORRECT and was left alone:
  isKeysymDown() genuinely takes an xkb_keysym_t.
- TESTS: new tests/t-keydeliver.sh, VERIFIED TO FAIL on the old code
  (7 failures, naming the bug). What it asserts, and why, is measured
  rather than assumed: it CANNOT assert delivered bytes, because pass()
  stamps the event with state()->m_timeLastMs, which only a REAL key
  event sets — under the harness a correct, explicitly-keycoded send
  still delivers 0 bytes to a focused `cat`, with a keyboard present and
  no error. So it pins the RESOLUTION, the half the bug was in and the
  half a harness can see: keycode tokens accepted (only the resolver
  knows them) and off-keymap keysyms refused (only the resolver checks).
  Deliberately NOT asserted: a junk NAME like "notakey", where
  resolveKeycode NoSymbol-matches the first unmapped keycode — upstream
  behaviour, not this bug, and pinning it would encode a quirk.
- Not asserted anywhere and worth saying plainly: END-TO-END DELIVERY to
  a focused app is only observable in a live session. This fix was NOT
  confirmed by pressing C-f in Firefox — that is Chris's check to make.

== THE RELOAD NO LONGER RE-READS THE MACHINERY: an explicit reset instead ==
- The machinery (kernel, core, enums, values, the 14 families, extras,
  emacs-keymaps) is now loaded ONCE per process. init.scm is still read on every
  generation, but every use-modules in it is a no-op after the first — which is
  what the module objects, and the gsubrs the host registered into the kernel,
  rely on. `reload-module`, the `in?` probe and the `use-or-reload-modules`
  macro are GONE from init.scm.
- The cost of that reuse is that a module's top-level state now OUTLIVES the
  generation, where re-reading it used to reset it by accident. A set! from a
  config on an EXPORTED binding writes into the EXPORTING module's cell, so the
  old behaviour was load-bearing: with reload-module removed and nothing in its
  place, t-api's `(set! hl--watchdog-ms 999999)` + reload test kept 999999, and
  t-watchdog failed downstream of it.
- So a module that keeps state defines an UNEXPORTED `reset`, and the sweep at
  the end of init.scm calls them all, once per generation, after every module is
  imported and before the config is read. Written for the only two modules that
  have state — kernel (watchdog budget/rearm/stack/handler) and emacs-keymaps
  (its three submap tables) — and nothing is registered anywhere, so a module
  cannot be forgotten from a list. The sweep runs on every generation including
  the first, where it is a no-op.
- THE SUBTLETY THAT COST THE FIRST ATTEMPT: the sweep iterates `module-uses`,
  which holds each module's PUBLIC INTERFACE, not the module. use-modules is
  module-use! on resolve-interface, and an interface carries only the EXPORTED
  names — so an unexported `reset` is simply not in one. The first version found
  nothing and silently did nothing (calling it by hand returned cleanly and
  changed no value). Probed and confirmed for (hyprscheme kernel): the use-list
  entry has module-kind `interface`, the resolved name has `directory`, they are
  not eq?, and module-local-variable answers #f for the former and the variable
  for the latter. The fix resolves each entry's NAME back to the module.
- `module-local-variable`, not `module-variable`, is the predicate — the latter
  answers for imported bindings too, so a module merely USING something named
  `reset` would look as though it owned one. tools/module-audit.py carries a
  named UNEXPORTED exception for `reset`, with its reason, because its
  every-define-is-exported rule is exactly right otherwise.
- Also fixed: the host clears `hl--ready` BEFORE reading init.scm. The kernel's
  file being re-read each generation used to re-set it to #f; loaded once, it
  would still be #t from the previous generation and the host's "did the API
  finish loading" check would be vacuous.
- Tests: t-api asserts the kernel variable is back to 5000 after a reload, and
  now also that emacs-keymaps' submap table is EMPTY again — reaching the
  unexported table the way the sweep does (resolve the module, take its own
  binding). Verified to fail: the submap assertion reports "[1] want [0]" with
  `(define (reset) #f)` in emacs-keymaps. 20/20 suite; make check clean, 7/7.
- Consequence to know: a machinery .scm edit NO LONGER takes effect on a config
  reload — the plugin has to be loaded afresh (a session restart). The wiki's
  building-the-plugin page claimed the opposite and was corrected, as was the
  loader section of CLAUDE.md.
- PARKED, and worth knowing why: this pass began as a memory-leak hunt. The
  generation module is permanently rooted by Guile — beautify-user-module! calls
  module-name, and module-name on an UNNAMED module names it AND registers it in
  the root module (boot-9.scm:3198; upstream bug#19235, 2014, still open, same
  class as bug#77374, 2025). Measured with a guardian test: make-module is
  collectable, make-module + beautify-user-module! is not, and pre-naming the
  module before beautifying makes it collectable again — but one retained
  generation costs ~5 kB against a ~885 kB/reload leak, so it is NOT the main
  term, and the bulk (~800 kB/reload, fixed, independent of config size, absent
  with the plugin unloaded) is still unexplained. Agreed not to chase a Guile
  design issue; the leak is documented here rather than fixed.

== NO MORE SHADOWS: `load` and `eval` are gone, `hl-load` is public ==
- The kernel used to redefine Guile's `load` and `eval` for every later file:
  `load` so a config's (load "x.scm") landed in the generation, `eval` to match.
  Both shadows are GONE, and neither name is on the kernel's export list any
  more. Machinery that silently redefines a core binding is a trap.
- `hl-load` replaces the load half — a public function in (hyprscheme core),
  exported and documented like anything else, next to the other plumbing. It is
  the same load said out loud, with the target NAMED (hl--c-generation) rather
  than assumed from the current module. It still answers whether the FILE
  loaded (#f when it raised, having reported to the log), which is what
  hl-load-config builds on, and hl-load-config now calls it by that name.
- EVAL NEEDED NO REPLACEMENT AT ALL, which is the part worth remembering: with
  no environment `(eval x)` evaluates in (current-module), and the host leaves
  the GENERATION current after buildGeneration succeeds — the success path
  never restores the old module. So a bare eval was already landing where the
  shadow was putting it; the shadow bought the appearance of control, not the
  thing. Nothing in the machinery or in the test config used a bare (eval ...).
- Where the no-generation fallback goes: hl-load loads into whatever module is
  current, via PRIMITIVE-LOAD and not `load`. Not a style choice —
  compile-lint rejected `load` outright in (hyprscheme core): "Use of `load' in
  declarative module", because a declarative module promises no bindings are
  added at runtime, which is exactly what load does. Verified to fail before
  the fix; the only visible cost is that a RELATIVE path is not searched for on
  %load-path, and every caller passes a path it built.
- The kernel stays #:declarative? #f, but NOT for the old reason — it is
  nothing to do with shadows now. It stays because the HOST modifies the kernel
  after it is read: it assigns every gsubr into the exported placeholders
  (registerAllBindings) and it sets hl--ready. Both reasons are in CLAUDE.md.
- Side effect worth having: the "imported module (hyprscheme kernel) overrides
  core binding `load'" warning is gone from every harness, and compile-lint
  reports zero warnings. NOT "warning-free" overall, and the difference is worth
  stating exactly: the C++ build still emits 72 -Wvolatile warnings, every one
  originating inside /usr/include/guile/3.0/libguile/scm.h's own macros — the
  unavoidable kind CLAUDE.md allows. Nothing in src/ warns.
- Tests: t-zz-example loads examples/hyprland.scm through hl-load — it needed
  the guarded one anyway, since its whole method is diffing the compositor log
  and a bare load no longer logs. t-api asserts hl-load answers #f for the file
  that raises, reusing the same broken file hl-load-config is tested with, so
  t-zzzz-exit's existing allowance covers the second error line. t-coverage's
  introspected list picked hl-load up on its own. 20/20; make check clean, 7/7,
  no lint warnings (see the side-effect bullet above for why that is not the
  same as "no warnings").
- Docs: the wiki's split-config example (core.md) and scheme-utilities.md now
  use hl-load, and both say plainly that bare `load` still works but RAISES —
  a raise at the top level of a config ends the load there. Both new blocks are
  listed in tests/wiki-examples.skip: loading a file the harness does not have
  answers #f and the block passes, but it leaves a log line behind, and
  t-zzzz-exit counts those. doc-audit's API count moved 716 -> 714, exactly the
  three kernel names removed (hl--load, hl--base-load, hl--base-eval) minus
  hl-load added; api-check reported the addition and no removal, and the
  snapshot was rebaselined.
- STILL OUTSTANDING from the same directive: watching files a config loads from
  OUTSIDE its own directory. The host watches the config file plus any .scm
  SIBLING in its directory, so a split config beside hyprland.scm is covered
  already — a load from elsewhere is not seen (Host.cpp drainWatch says so).
  RESEARCHED, SO NOBODY REPEATS IT: Guile itself has NO inotify interface —
  verified, no inotify symbol in libguile-3.0.so (any soname) and no *inotify*
  file anywhere in its install tree. The third-party `guile-inotify` (github
  b4283) does exist, and is a hard blocker rather than an option: it is GPL-3.0
  and this project is BSD (packaging/PKGBUILD:20), so vendoring it relicenses
  the tree. It is also a 2012 five-commit, five-star wrapper for Guile 2.0 with
  no releases and no documented API. And it would not remove the C++: it wraps
  inotify_init/add_watch/read, while the wiring — which directory to watch,
  matching an event's name back to a path, and handing the fd to Hyprland's
  event loop via doOnReadable — has to be where the event loop is.
  An implementation of this (%load-hook in the kernel + a gsubr + per-directory
  watches keyed by wd) was WRITTEN AND THEN REMOVED at the user's request. The
  gap stands as it was: nothing was left behind, in either language.
  -> CLOSED in the next entry below, by different means: inotify is bound from
     SCHEME with (system foreign), so the C++ is one generic gsubr and the
     "which files" decision never leaves Scheme.

== WATCHING WHAT A CONFIG LOADED, with inotify bound from Scheme ==
- THE GAP: the host loads exactly ONE file — the config — and nothing in it says
  what it reached, so a (hl-load "…") pointing outside the config's directory was
  invisible: no watch, no reload, silent. The INTERPRETER knows, because it did
  the loading.
- THE SHAPE, which is the part worth copying later: %load-hook (Guile's own "a
  file is being loaded" notification) records every path the loader reads; the
  machinery watches each one's DIRECTORY and reloads an event that matches a
  recorded path. The only C++ is ONE GENERIC PRIMITIVE — hl--c-on-readable, "call
  this thunk when this fd is readable" — which knows nothing about inotify or
  config files and is reusable for any fd. Every decision stayed in Scheme.
- INOTIFY ITSELF IS BOUND FROM SCHEME with (system foreign) — no C, no
  dependency. (hyprscheme inotify) is the libc boundary module and is EXCLUDED
  WHOLESALE from the API by tools/api-names.scm, alongside the kernel, with the
  reason written down: it is a table of foreign bindings, not API, and its names
  are inotify(7)'s on purpose so they can be checked against the header.
  (hyprscheme watch) is the policy — a composer, since it calls
  hl-config-reload!, which a family owns.
- WHY THIS AND NOT THE ALTERNATIVES: Guile has no inotify of its own (verified:
  no symbol in libguile, no file in its tree) and the third-party guile-inotify
  is GPL-3.0 while this tree is BSD — a licence blocker, not a preference. The
  C++-only version that was tried first was removed at the user's request on the
  grounds that it put in C++ what Scheme could do; this does the opposite and is
  smaller for it.
- THREE BUGS FIXED ON THE WAY IN, all in the binding as first drafted:
  (1) it parsed only the FIRST event of a read — a read returns every queued
  event concatenated, so the tail was dropped and a reload silently missed;
  (2) it redefined Guile's own `pointer->procedure`, shadowing the import, so
  anything else in the module wanting the real one got the wrong function (now
  `libc-procedure`, which takes a NAME where Guile's takes a pointer);
  (3) `rassoc` is in neither (guile) nor srfi-1 — compile-lint said so, and the
  two alist lookups are now written out rather than reached for.
- ONE BEHAVIOUR CHANGE, deliberate and worth flagging: the host's "ANY .scm
  beside the config reloads it" heuristic is GONE. It existed only because the
  host could not know what a config loaded. Keeping it alongside the new watcher
  would fire a SECOND reload for every edit to a split config beside
  hyprland.scm — which is the documented arrangement, so the common case. The
  config file itself is still watched by the host (symlink-resolved), and
  everything else a config reads is covered by the watcher, wherever it lives.
- Tests: t-config loads a scratch file from OUTSIDE the config directory, edits
  THAT file, and requires the config to come back — the marker it writes is only
  run because the config re-ran and re-loaded it. VERIFIED TO FAIL: with the
  hl--c-on-readable registration neutered the test reports "did not reload
  (marker=0)", so it is testing the watch rather than passing for another reason.
  t-api asserts the file a config loaded appears in hl-loaded-files (which is how
  the hook is observable at all). 20/20; make check 7/7; api-check reported ONE
  addition, hl-loaded-files, and no removals, and the snapshot was rebaselined.

== COLOURS ARE NUMBERS; strings go through string->color ==
- A colour is now a 0xAARRGGBB INTEGER everywhere in the API — alpha first, the
  packed-ARGB32 layout CHyprColor's uint64_t constructor reads. Scheme has hex
  literals, so a config writes (hl-notify! "hi" 5000 #:color #xffffa500) and
  nothing is parsed. The gsubrs take SCM and convert with colorFromNumber.
- A STRING IS REFUSED by a colour argument, on purpose. Hyprland's config-file
  spellings still work but only through a new, deliberate function:
  string->color (in core, so every module and config reaches it) answers the
  integer or #f. It delegates to Config::ParserUtils::parseColor — the
  compositor's OWN parser, the one the config file, the rule engine, the IPC
  commands and the scripting API all use — so our acceptance set is Hyprland's
  by construction, the same argument as resolveKeycode for keysyms.
- WHAT THIS FIXED. The old schemeColorFromStr accepted bare hex digits
  ("FFA500FF") that Hyprland's parser REJECTS — an invented spelling — and
  refused rgba(...) that Hyprland ACCEPTS: both stricter and more permissive
  than the format it claimed to implement. Worse, the reader returned an
  integer while the setter demanded a string, so
  (hl-notification-color-set! n (hl-notification-color n)) was impossible. The
  parity gap is why rgba(ffa500ff) worked in bindings.lua and failed in
  bindings.scm.
- hl-notify!'s absent colour is #f, not 0: 0 is a legal colour (transparent
  black), so #f is what means "the icon's default".
- THE TESTS ARE MEASURED, NOT GUESSED. Seven spellings pinned against expected
  decimal integers, and the expectations were verified by linking the tree's own
  ParserUtils.cpp.o and printing what the compositor's parser actually answers —
  all eleven rows matched, including the two refusals ("red", "FFA500FF"). The
  load-bearing one is "#00ff00ff" -> #xff00ff00: a hex passthrough would say
  #x00ff00ff, so it fails the moment anyone "simplifies" the string path. Also
  pinned: "#fa5f" (four digits) is #f, since the parser takes 3, 6 or 8 only.
- Tests also cover the round trip that used to be impossible, and that a STRING
  is refused by the setter. t-api had one older call site still passing a string
  ("0x80FF80FF") — the new code caught it, which is the change working.
- Docs: notifications.md gained a Colours section — the alpha-first layout, the
  #xffa500ff trap spelled out, and string->color with its full accepted set.
  CLAUDE.md gained a COLOURS convention.
- 316 gsubrs registered/called (was 315); 20/20 suite; make check 7/7.

== THE MACHINERY COMPILER WAS BROKEN, AND hyprpm HID IT ==
- `make scm-compile` was aborting with a CORE DUMP and hyprpm still reported the
  build as successful, so this user's installed machinery sat at the last good
  copy (00:34) while the plugin updated — which is why the new (hyprscheme
  watch) auto-reload was not live in their session at all.
- THE CAUSE WAS MINE, and the trap is worth knowing. guild compile runs with the
  machinery dir on GUILE_LOAD_PATH (it must — modules resolve each other by name
  from there), and GUILE EVALUATES <load-path>/init.scm AT STARTUP. So compiling
  ANY module evaluates init.scm, which imports everything and runs each module's
  top level. watch.scm called hl--c-on-readable at its top level; that gsubr
  exists only inside the compositor, so a plain guile died with
  "Unbound variable: hl--c-on-readable" -> "Aborted (core dumped)". Verified by
  putting a (display ...) in an init.scm on the load path and watching it print
  during an unrelated module's compile.
- WHY NOTHING CAUGHT IT: scm-compile is NOT part of `make check`, so every lint
  I ran all session was green. `install` and `hyprpm-machinery` both depend on
  it, so both were broken too — and bind-audit, module-audit and compile-lint
  all passed throughout.
- THE FIX: watch.scm's top level now only DEFINES. The fd is opened and the
  arming attempted under a `guard`; outside the compositor it fails harmlessly,
  the fd is closed, and hl--watch-armed? stays #f with the hook inert. The
  kernel's "keep the top level to defines" rule is the same rule, one module
  earlier, and CLAUDE.md now states it generally.
- HONEST LIMIT OF THE GUARD: it makes the arming failure invisible to
  load-check and compile-lint, so a real arming bug would show up only in the
  compositor — where t-config's watcher test covers it (verified to fail with
  the registration neutered).
